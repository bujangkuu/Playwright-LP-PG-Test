## 1. Requirement Summary & UI/UX Design Analysis

Fitur **`Reconcile`** dirancang sebagai antarmuka otomatis dan backend pemrosesan rekonsiliasi data transaksi antara sistem Payment Gateway LintasPay dengan pihak Bank/Acquirer (saat ini mendukung **Bank Nobu** dan **Bank Inacash**). Fitur ini memungkinkan pengguna internal (Internal Admin) untuk memilih Acquirer, menentukan tanggal transaksi bisnis, mengunggah file mutasi/reconciliation report dari bank (format **`.csv`** atau **`.xlsx`** hingga **100MB**), membandingkan data LintasPay vs Acquirer secara otomatis, menyeleksi transaksi yang ada di bank namun belum tercatat di LintasPay (unmatched data), mengeksekusi penyisipan data (*batch insert*), dan menyajikan laporan hasil rekonsiliasi.

### Alur Kerja UI/UX (Berdasarkan 5 Layar Desain Prototipe):
1. **Layar 1 (Form Input & Validasi Wajib)**:
   * Dropdown **`Acquirer *`**: Memuat 2 opsi eksklusif: **`Nobu`** dan **`Inacash`**. Jika di-blur tanpa pilihan, muncul inline error *"Acquirer is required"*.
   * Date picker **`Date *`**: Format tanggal baku `DD/MM/YYYY` (misal: `20/01/2026`).
   * Dropzone **`File Reconcile *`**: Menerima file `.csv` atau `.xlsx` dengan batas ukuran maksimal 100MB.
   * Tombol **`Import`**: Berstatus disabled saat salah satu field belum terisi lengkap.
2. **Layar 2 (File Terpilih & Form Lengkap)**:
   * Menampilkan kartu file hijau di dropzone memuat ikon spreadsheet, nama file (misal: `file.xlsx`), ukuran file (`21.89 kB`), dan tombol silang (`x`) untuk batal.
   * Tombol **`Import`** berubah menjadi aktif (biru cerah).
3. **Layar 3 (Kartu Ringkasan Selisih & Tabel Unmatched Transactions)**:
   * **3 Kartu Metrik Ringkasan**:
     1. **`LintasPay`**: Total nominal transaksi internal (misal: `Rp50.000.000`) dan counter (`1.234 transactions`).
     2. **`{Nama Acquirer}`** (Dinamis: **`Nobu`** / **`Inacash`**): Total nominal mutasi bank (misal: `Rp320.123.000`) dan counter (`1.234 transactions`).
     3. **`Difference`**: Selisih nominal transaksi (misal: `Rp1.000.000`) dan counter (`1.234 transactions`).
   * **Tabel `List Transaction Reconcile`**:
     - Menampilkan transaksi yang tercatat di mutasi Acquirer namun belum ada di LintasPay.
     - Kolom: `Checkbox`, `Date Time`, `MPAN`, `RRN`, `Amount` (Rp), dan `MTN`.
     - Master checkbox header dan checkbox baris individual.
     - Kontrol pagination (`Show 10`, counter items, `< Previous`, `Next >`).
     - Tombol aksi: **`Proceed`** (aktif jika >= 1 baris tercentang) dan **`Cancel`** (mereset centang).
4. **Layar 4 (Modal Dialog Confirm Reconcile)**:
   * Muncul saat tombol Proceed ditekan.
   * Judul **`Confirm Reconcile`**, pesan *"Are you sure you want to process this transaction?"*, tombol **`Cancel`**, dan tombol **`Process`** (biru).
5. **Layar 5 (Hasil Eksekusi & Pemisahan Tabel)**:
   * Tabel dipecah menjadi dua: **`Successful (N)`** dan **`Failed (M)`**.
   * Tombol **`Done`** berwarna biru di bawah halaman.
   * Floating popup **`Process Completed`** di sudut kanan bawah menampilkan progress bar 100%, rasio eksekusi (*X/Y*), tanggal, pill hijau **`Successful N`**, dan pill merah muda **`Failed M`**.

## 3. Requirement Clarification & Gap Analysis

| No | Poin Analisis / Potensi Celah | Temuan & Rekomendasi QA | Tindakan Mitigasi |
|---|---|---|---|
| 1 | **Dukungan Dua Format Acquirer (Nobu & Inacash)** | Nobu memiliki 19 kolom header, sedangkan Inacash memiliki 13 kolom header dengan penamaan yang sangat berbeda. | Parser backend wajib membaca metadata Acquirer terpilih dan mencocokkan skema header yang relevan secara ketat. |
| 2 | **Pencegahan Human Error (Schema Mismatch)** | Operator dapat salah memilih dropdown (misal memilih Nobu) namun mengunggah file Inacash, atau sebaliknya. | Sistem wajib memvalidasi kecocokan kolom header sebelum parsing baris data, menolak file dengan pesan informatif *Schema mismatch*. |
| 3 | **Filter Status Sukses per Acquirer** | Pada Nobu, baris sukses ditandai `STATUS: Berhasil`. Pada Inacash, baris sukses ditandai `Status: SUCCESS` dan `Settlement Status: ACTIVE`. | Parser hanya memasukkan transaksi yang berstatus sukses/aktif ke dalam tabel List Transaction Reconcile. |
| 4 | **Format Tanggal Serial Excel pada Inacash** | Kolom `Paid At` / `Created At` pada Inacash diekspor dalam format serial date Excel (misal: `46188,61248`). | Parser backend wajib mengonversi serial date Excel menjadi format tanggal baku `DD/MM/YYYY HH:mm:ss` di UI tabel. |
| 5 | **Pencegahan Double Processing (Idempotency)** | Menjalankan reconcile ulang pada tanggal dan file yang sama tidak boleh menyebabkan double insert pada transaksi yang sudah berhasil di-reconcile. | Backend menerapkan unique constraint pada kombinasi `RRN` + `Acquirer` + `Date` dan idempotency guard. |

## 5. Risk Analysis & Mitigation Strategy (Analisis Risiko Produksi)

| Risiko Pengujian | Tingkat Keparahan | Dampak | Rencana Mitigasi QA |
|---|---|---|---|
| **Data Duplication & Double Balance** | **CRITICAL** | Jika transaksi selisih bank dimasukkan dua kali tanpa deduplikasi unik, saldo transaksi merchant dapat tercatat ganda. | Pengujian validasi unique constraint `RRN` + `MTN` di database dan verifikasi idempotency guard pada backend. |
| **Cross-Acquirer Schema Corruption** | **HIGH** | File Inacash diparsing menggunakan parser Nobu menghasilkan pergeseran kolom Amount atau RRN. | Implementasi validasi skema ketat (*strict schema check*) sebelum data diproses ke database. |
| **Parsing Failure on 100MB File** | **HIGH** | File statement berukuran mendekati 100MB dengan puluhan ribu baris dapat menyebabkan server out-of-memory (OOM) atau timeout. | Menjalankan uji stress boundary 50MB-100MB, verifikasi streaming XLSX/CSV parser, dan penanganan timeout request. |
| **Unauthorized Exposure of Bank Statement** | **HIGH** | User tenant luar (Merchant/Organization) mencoba mengakses mutasi bank acquirer melalui endpoint API internal. | Memverifikasi enforcement permission internal pada gateway API dan menolak seluruh user non-internal dengan `HTTP 403`. |
| **Excel / CSV Formula Injection** | **MEDIUM** | Karakter formula jahat pada kolom teks dieksekusi saat data diunduh atau ditampilkan ke antarmuka web. | Menerapkan sanitasi input otomatis dan escaping pada seluruh field teks sebelum disimpan dan dirender ke DOM. |
